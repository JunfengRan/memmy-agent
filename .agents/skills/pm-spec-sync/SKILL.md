# 规格同步

`design-docs/standard/` 是钉钉文档的本地镜像，不进 git。代码对齐的版本记在 `docs/project-memory/spec-snapshots.md`。

## 步骤

1. 列出 `design-docs/standard/` 下的文件，计算 sha256：
   ```bash
   shasum -a 256 design-docs/standard/*.md
   ```
   与 `spec-snapshots.md` 最新一组记录比对。没有变化就告诉用户并结束。
2. 判定权威文档：文件名中版本号最大的架构文档（`项目记忆：端云协同架构与模块设计（vN）`）是最高权威，见 ADR-0001。出现新版本时，旧版只作参照。
3. 找出变化：
   - 读新文档的修订记录（PRD、SDK 规格在文末「修订记录」，架构文档在开头版本行和第 6 节）。
   - 按章节比对与上次对齐内容的差别。重点看：§1.6 接口、§2 写入链路、§3 读取链路、§5.3 表结构、§5.1.5 错误码、§6.1 已定口径、§6.4 与 PRD 差异、各节验收表。
   - 如果上次快照的文档已经被覆盖，就以 `spec-alignment.md` 记录的行为为旧基线逐节比对。
4. 更新文档：
   - `spec-snapshots.md` 最上面追加一行：日期、文件名、文档内日期/修订、sha256 前 12 位、变化摘要。
   - `spec-alignment.md`：受影响的行状态改为 `待重新对齐`，备注写变化点；第二节差异表增删对应条目。
   - `open-questions.md`：新规格回答了的问题改为 `已关闭`；新的 TBD 或矛盾追加为新条目。
   - 变化涉及契约、表结构或已定决策时，按 `decisions/0000-template.md` 起草 ADR，状态写「提议」。
   - `ROADMAP.md`：受影响条目在备注里写明变化；需要新增或移动的条目照改，并在变更记录加一行。
5. 向用户汇报：变化清单（按 L1 只改文档 / L2 契约或表 / L3 算法或提示词分级）、受影响的代码和测试、建议的 Roadmap 调整。L2、L3 变化在用户确认前不改代码。

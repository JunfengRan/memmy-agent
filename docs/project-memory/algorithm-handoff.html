项目记忆为什么难

项目记忆的核心是把会话整理成可持续更新的共享状态。难点贯穿抽取、主题归属、冲突裁决与检索呈现；接口已能作为基座，效果问题要沿证据链定位。

01先理解这份基座

项目记忆解决的是多人、多 Agent 共同推进一个项目时，结论散在不同会话里的问题。接手者需要知道现在按什么做、为什么变了、谁还有不同意见，以及哪些工作已经完成。只保存聊天记录会把找上下文的工作留给下一位；只保存一段摘要，又容易把过程、分歧和当前状态压成一句话。

当前开发分支已经提供项目记忆的本地接口与整理、检索、注入链路，可以作为后续开发基座。这里的“完成”指已有可接入的实现；不表示所有算法目标均达标，也不表示云端实现与最终验收已经完成。W48 的云端 Store、故障注入与验收表仍是后续工作。

概念职责通知服务例子（教学示例）
Space项目共享边界，存放项目指令、领域和主题团队的通知服务
domain由调用方指定的范围；模型不自行判定领域服务可靠性
topic围绕一项工作组织的知识，不等于聊天会话失败重试策略
decision当前约定及其作者、未决分歧、历史失败后最多重试三次
experience可复用的经验，允许保留历史，不挂 conflicts先检查幂等键，再排查重复通知
timeline发生过的工作进展已上线重试监控

默认路径由本机完成抽取、归属与判断，再通过 ProjectMemoryStore 读取和提交。存储层不调用模型。对外入口统一在 /api/openmem/v1/。接口实现见 api.ts；状态和待办见 上手说明、Roadmap。

02一轮消息如何成为记忆

下面是一组新编的通知服务会话，用于解释机制，不是测评样本，也不是对当前模型输出的实测承诺。调用方先选择 Space 和唯一的 domain“服务可靠性”。成员甲说：“通知失败最多重试三次，因为下游对突发请求敏感。”助手答：“已按三次配置，并补充失败计数。”

  1. 采集。保存原始轮次，剥离此前注入的记忆，避免“检索出来的话又被当作新事实”形成回声。时间与作者来自消息，不能让模型补造。
  2. 抽取。“最多三次”是约定，“已补计数”可能是进展；“因为下游敏感”只能在原文确有依据时保留。草稿不读候选主题，避免主题反过来诱导要写什么。
  3. 召回与归属。每条草稿发一条召回 query；候选并集通常上限 20，必须考虑的主题不受此限。M04 看候选的领域、摘要和描述，决定归到哪里。未知主题 id 进入推迟，不擅自新建。
  4. 判断。已归入既有主题的草稿，才读取完整条目并交 M05 判断。全是新主题时没有旧决策要比较，可以跳过这次调用。当前实现也在 M05 提议主题摘要和描述改写。
  5. 合并和提交。代码根据作者、时间、认可与判断信号生成动作，再带 expectedRevision 提交。存储只执行经过校验的动作，不自行解释会话。

同一任务的抽取只执行一次。主题集合变化，要重新召回与归属；条目版本冲突，只重读并重跑判断与合并，不重放旧 ChangeSet。总提交尝试预算最多三次。比如另一个 Agent 抢先修改了“三次”，当前任务不能把基于旧内容生成的动作直接覆盖回去。

完整阶段约定见 ADR-0007。它记录了当时的版本号；当前提示词版本应看源码和具体评测记录。

03复杂性藏在状态变化里

“不写过程”不能变成“丢掉约定的一半”

“打开文件看一下”通常是执行步骤；“失败记录固定写入 retries.ndjson”可能已经规定了后续接口依赖的产物；“已删除临时降级开关”是当前状态。三个句子都像实现细节，是否保留却取决于它是否承载项目可复用的事实。q07 和 q14 正是在这条边界上丢了文件名、已完成删除的信息。

同一句话，复述与新增的区别来自已有状态

成员甲首次说“三次”，助手复述，不能把两句话都当作已经记过而丢掉。下一轮在同一 Space、同一 domain 已经整理过的消息，可以只作上下文。若甲说“现在改五次”，即使句子大半相同，也发生了状态变化。q42 中首次出现的约定被两次标为 restatement，最终没有任何草稿。

不同意见不等于已经替换

会话与条件应理解的状态变化
甲已提出三次；乙另提五次，没有认可证据保留甲的 content，乙的不同结论进入 conflicts
甲明确认可五次，并能定位到同一决策可进入改写或裁决路径；原结论进入 history，具体动作由规则和信号决定
甲只是继续说三次可能只是加入已有结论或复述，不新增一条当前决策
迟交的旧会话建议两次不能改写时间更晚的当前决策；依据迟交与作者规则处理

history 是已经发生的版本变化，conflicts 是尚未收敛的不同结论。清空 conflicts 时必须在同一事务写入 history。不能因“这次文字更像最新方案”就越过认可关系。内容作者加入已有 conflict 而挪空当前成员的边界仍待 Q-23 裁决，不能在交接稿里写成已解决。

推迟是等待证据，也会造成暂时不可检索

“刚才那个改动撤回了”没有可定位的工作时，应等待同会话后续上下文；但“重试监控已撤回”已有明确对象时，过度推迟就会让 Search 看不到完成状态。回填只处理同一会话、同一 Space 的适用片段，不代表所有推迟内容在任何提问前都能补齐。q16 的撤回已被抽取，却停在 deferred 表里。

作者、时间、Space 与 domain 是写入语义的一部分。重发网络请求应保持原 chat_time；没有时间时按到达时间的秒处理，同一秒同文仍可能归为同一任务。任务幂等解决重复提交，不能代替对多轮会话含义的判断。

04主题召回以后，还有一道门

项目一路结合词面、向量名次与确定性信号，再参与跨路融合；默认不调用模型重排。候选主题会进行 MMR 选择与数量截断，条目有自己的词面门槛。主题摘要和描述仍可能被返回，而该主题下的决策正文却已经被删掉。q04 的冲突正是在这里消失：主题已召回，带 conflicts 的决策未被保留，阅读模型只看到旧的主题描述。

条目门槛来自 query token 数：至少需要 max(1, ceil(queryTokens × 0.2)) 个词面命中。它不直接判断冲突对答题是否关键。提高主题 Recall@K 无法自动修好这种条目缺失；同样，抽取已丢掉的句子，也不能靠放宽检索门槛找回来。

三路失败通过 degraded 表达，可能仍是成功信封，调用方必须检查。只请求 project 就只运行项目一路；省略 include_memory_view 则默认运行用户记忆与 L1/Skill，不搜索项目。这是当前实现，缺省行为的设计确认仍记在 Q-28。

05topic 切得细，为什么仍然会错

topic 要同时支持稳定归属、定位需要更新的旧决策、检索相关内容和供人浏览。一项新改动既可独立交付，又会影响已有约定：只看“可独立交付”很容易新建主题；只看词汇相近，又会把不同工作合在一起。主题数量本身没有告诉我们哪一种错更多。

运行（v2.1）主题 / 金标B³ P / R / F1重复 / 误并条目 F1
当前 A65 / 500.855 / 0.559 / 0.67610 / 10.816
当前 B58 / 500.894 / 0.575 / 0.7009 / 30.861
旧实现30 / 50见原报告；F1 0.4071 / 20.487

上表 P/R 需与原报告一致，附录生成脚本会校验主题数、B³ F1 和错误计数。重复率与误并率的分母不同于主题总数，不能用“58−50=8”代替 9 次重复计数。运行 B 的正文完全相等匹配只对上 2 条必写条目，无法复现评分器的 9 / 3，因此完整陈列不冒充逐主题错误标注。

q31：拆成两项“当前工作”，裁决找不到旧结论

旧主题说“金额继续写在 journal 正文”；新消息说“改成 entries.amount”，归属阶段新建了另一个金额主题，且没有对照旧决策。随后“以周工的为准”已抽出 resolve 信号，却只归到新主题。判断把它当作与新内容相同，resolve 为空。旧主题仍保持当前状态，Search 同时返回两种口径。这里既有归属造成的隔离，也有判断未完成裁决，不能归结为“主题多一点只是界面难看”。

建议：把展示归纳与算法匹配分开讨论

一种待验证方向是保留可追踪的细 topic，再把相关主题归纳成面向人的工作列表；展示归纳不反过来替代写入匹配键。这个方向还没有进 v3，也没有实现。它能否改善跨主题更新、归纳什么时候刷新、人修改后如何同步，都需要单独设计与评测。当前数据也不能证明“越细越好”；细主题仍可能拆散同一决策。

指标及记录见 R-20261111-01、评测集方案。

06九道错题怎样定位

材料是带追踪跑次 R-20261111-06：answers.llm 0.710，entries.f1 0.828，Recall@3 0.903，entryHit 0.355。这次独立记录，不合并进前两次均值。31 道计分题中 9 道答错；以下按现有 RCA 的主因分组，不把主因理解成唯一原因。

题目主因直接证据影响与共同因素
q04检索条目过滤不同结论已在 conflicts，决策 kept=false主题召回成功仍只读到旧描述
q06抽取丢句取整被标 local_implementation保留两位小数被缩成格式化
q07抽取丢句prices.csv 随实现细节整句丢弃格式被记住，文件名丢失
q14抽取丢句已删除连接串的完成状态被丢弃今后不写，不能证明现在已删除
q15抽取丢句诊断标 process_material / restatement同轮撤回又被推迟，原因与进展都不可见
q16延迟写入已撤回抽到但 work_unresolved片段在 deferred，不在可搜索主题
q17判断未更新topic_updates 为空，描述仍是旧规则同时有诊断丢句、撤回推迟、条目被滤
q31判断未裁决resolve 信号被判空，旧主题没入历史此前归属新建重复主题，只匹配新主题
q42抽取丢句首次约定两句都判 restatement草稿为空，后续归属和判断都没执行

主因计数是抽取 5、判断 2、推迟 1、检索条目过滤 1。先问“答题事实是否以原句或同义内容进入可检索状态”，再查草稿、归属、判断、提交、条目保留和最终 reader.user。这比看到错误就调 Top-K 更能定位修复层。

不要用一个字段替代归因

locations 是金标整句的定位结果，空数组只说明整句未命中，不能直接证明库里没有事实。q04 的同义内容已在 conflicts；q07 的 entryHit=1，但文件名仍丢失。entryHit、整句定位、语义正确性是三种检查。

现有追踪没有发现一道“正确关键信息完整呈现给阅读模型，模型仍把它读错”的独立主因。但 q31 的回答也把两个已确定描述改写为“尚未确定”，阅读侧仍有表述问题。8 道非 q04 题各自缺少、过时或未正确组织关键事实，不能进一步推断阅读模型完全没有问题。另有 12 道答对但 entryHit=0，本轮未逐题分析。

RCA 中的修复方向是后续假设，不是本次实现。特别是不能为了修一题就把所有文件名都写成决策，也不能把所有新结论直接覆盖旧内容。抽取边界待 Q-11 / Q-36 讨论；q04 应验证关键冲突能否到达阅读上下文；q31 必须核对旧决策历史是否真实发生，而非只改一段摘要。

07从接口接入，而不是复制算法

下列是 HTTP 路径与 JSON 请求体示例；通过已有鉴权访问服务，不包含地址、端口或真实身份。示例字段以当前 api.ts 为准，不需要改 SDK 公共契约。

先创建空间和领域

POST /api/openmem/v1/create/space
{
  "space_name": "通知服务",
  "instructions": "维护团队共享的通知服务决策与进展。",
  "domains": [
    {
      "domain": "服务可靠性",
      "description": "失败处理与运行约定"
    }
  ]
}

服务生成 space_id；不要自己传同名字段。保存成功信封 data 中的 space_id。domains 预先登记，本例只传一个领域，从而允许新建主题；多个候选领域不能由模型私自替调用方选。

POST /api/openmem/v1/get/status
{"task_id":"<add 返回的 task_id>"}

成功信封为 code=0。Add 受理返回 task_id 与 status，不等于整理已完成。轮询直到 completed 或 failed；running 时继续等待。任一 Space 失败会让任务最终标为 failed，但其他 Space 可能已经成功；公开 get/status 返回聚合结果与 error，不暴露内部逐 Space details，不能据此假定整批回滚。memory_views.project 包含主题 ids 与 deferred_count，推迟不等于已写成可检索条目。

显式搜索项目

POST /api/openmem/v1/search/memory
{
  "user_id": "member-a",
  "conversation_id": "notification-retry-demo",
  "space_ids": [
    "<同一个 space_id>"
  ],
  "domains": [
    "服务可靠性"
  ],
  "include_memory_view": [
    "project"
  ],
  "query": "通知失败重试几次，为什么？",
  "memory_limit_number": 9
}

读取 data.topic_detail_list；若有 data.degraded，按部分召回处理。relativity 是本次结果的相对值，不能把某个固定值跨请求解释为绝对概率。工具检索可额外传本机字段 recall_via="tool"；它不属于公开 SDK 参数。会话开始的索引通过 POST get/memory（space_id）读取；完整主题通过 GET get/memory/:id，data 仍是 topic_detail_list 数组，不是裸主题。

可重试的模型失败或版本冲突耗尽，再提交原批次会创建恢复任务；多 Space 时只重跑符合恢复条件的 Space。若存在不可重试失败，当前逻辑会保留原任务。先检查错误类别，再决定恢复，避免盲目创建新会话。

## 1. 金标满分和阅读上限不是一回事

`--oracle` 把标准答案直接写进 run，`answers.llm` 一定是 1。这只说明评分器认得自己的金标。

真正的上限是：在每个提问时刻渲染当时的 `topic_detail_list`，交给固定阅读模型作答，再交给评委打分。阅读模型答错，或评委把对的答案判错，上限就不到 1。这些分不是实现丢的。

v2 上这一上限是 0.826（19/23，R-20261105-03）。四道错题里，两道是摘要用了提问之后才出现的要点，一道是标准答案写成「已经修好」但金标里分歧还在，一道是阅读模型多说了一句无法确认。

网关模型列表里没有 `claude-haiku-5-5`，调用返回 503、`model_not_found`。v2.1 的上限改用当时能通的模型，温度都是 0，评委都是 `claude-haiku-4-5-20251001`。

## 3. 评委会把已经说对的答案判错

q24 问 catalog 的价格表为什么要加一列金额。阅读模型已经说出：价格查询太慢，给 price 表加 amount 列，列表直接读这一列，不再拼装说明文字。评委的理由是「这是另一张表、另一个需求」。

记忆里的决策本来就写着 price 表。标准答案当时没写出「price 表」这几个字，评委就自己补了一个「catalog 表」，再判定两者不同。把标准答案改成和决策同一组事实之后，同一评委判对。

同一道题、同一份回答，抽查时判对、全量跑时判错，也出现过一次。温度 0 不能当成「再跑一次结果一定一样」。

## 6. 产品回放还没有新的 entries.f1

`entries.f1` 衡量的是系统最终写下的决策、经验和进展，和金标必写条目对得上多少。评委先判断是不是同一件事，再一对一配对。召回率看该写的有没有写上，精确率看写下的有多少是该写的，F1 是两者的调和平均。门槛默认 0.8。

同样还没有新数的有：归类准确率、重复主题率、错误合并率的产品回放、每轮注入占全量的 30%、流水线 Recall@K、HTTP P95。

## 8. 实现里值得知道的行为

这些都已进代码，细节在 ADR 和 `open-questions.md`。

**整理只抽取一次。** 主题集合变了，重跑召回和归属，不重抽。版本冲突只重跑判断，最多 3 次，不重放旧的 ChangeSet。候选并集上限 20，标成必须考虑的主题不会被这层上限丢掉。

**排序不用模型，也不拼各路原始分数。** 三路按名次做 RRF，k=60。relativity 是这次融合分除以这次最高分，再按输出顺序取到目前为止的最小值，所以列表上的 relativity 不会回升。公开结果没有 `score`。

**省略** `include_memory_view` **时不搜项目。** 缺省走用户记忆和 L1/Skill。要搜项目必须显式带上 project。这个缺省不在 Q-28 原来的提议里，代码已经这样做，仍等设计确认。

**三路共用 1200 ms 超时，project 也在内。** 以前只搜项目时没有这层截止。超时后主题列表为空，并在 `degraded` 里记下 project。底层检索可能在返回之后仍写入 `recall_log`。

**一条过期向量会让整次项目召回退回词法。** 这是 v3 §3.5.1 的现行为，Q-30 还没改。

**注入进模型之前要拆掉闭合块。** 字段里如果出现字面的 `</project_index>` 或 `<memos_context`，会把块提前闭合，剥离时删错一段。这两类标签都换成全角。未闭合的标签原样留下并计数。

**非作者、未被认可的不同结论进 conflicts，不改写更晚的决策。** 内容作者加入已有分歧、从而把当前内容的成员挪空，这条路径还没改，记在 Q-23。对应用例是 `it.todo`。

**同一秒、同一段文本仍是一条任务。** 没有 `chat_time` 时用到达时间的秒。可重试失败（模型调用失败、版本冲突耗尽）再提交会新建任务，只重跑失败的 Space。新任务上的条数只含这次重跑的 Space，上一次已经写入的要看原任务。

## 9. Jev 和 Super Agent：切得细才纯，但会话会变碎

项目记忆在 add 时要决定一条消息归进哪个 topic，search 时要决定查哪张主题卡。旁边有两组实验看的是同一类问题的另一个版本：几路 Cursor 会话的消息交错进来，路由器要判断每一条属于哪个会话。

材料在 `eval/session-router-ablation/README.md`（2026-11-09，分支 `feat/superagent-session-router`）。本目录是副本，脚本依赖那个分支上的 `superagent-session-router.ts`，在当前开发分支上不能直接跑。原始输出在那次实验的 worktree：`.worktrees/superagent-session-router/eval/session-router/`。

### 两个协议本来不是同一个任务

**Jev** 是项目记忆里的选题实验，产品开关 `MEMMY_DECISION_TOPIC` 默认关闭。它把归属做成一道选择题：候选是已有主题卡（或会话卡），选项里还有 `new` 和 `none`。模型是 gpt-6-luna。这个模型不接受 `temperature: 0`，请求里不传温度。

Jev 自己的评测记在 R-20261106-01，和下面的会话消融不是同一件事，数字不能横比：

- 候选是金标主题卡（名称、摘要、描述），不经过产品 add/search。
- add 归属准确率 0.882（30/34）。已有主题 21/21 全对，新建 3/5，无关 6/8。
- 同一批卡片上，search 选中 Recall@1 是 0.826（19/23），词法对照是 0.522。按概率排序时 22/23 题的正确主题排第一，有 3 题模型最后选了 `none` 或 `new`，所以选中率低于概率排序。
- 词法对照的 add 归属只有 0.588，而且词法不会判「无关」。

**Super Agent** 是会话路由器，动作是 accept、attach、ignore、stop。提示词版本 `2026-11-06.1`。原来的实验用 DeepSeek，温度 0。它的设计是不确定就新建，不把「看起来相关」当成同一条请求。

### 消融在问：提升来自协议，还是来自模型

数据集沿用 Super Agent 实验：23 条消息，来自 6 个 Cursor 会话，按轮转交错。金标是「这条消息来自哪个原始会话」。同一个原始会话里可以有互不相关的请求，所以金标不是「同一件事」。

五个格子：

| 格子 | 协议 | 模型 |
| --- | --- | --- |
| baseline | 词法：和已有会话卡有 token 重叠就并入，否则新建 | 无 |
| Jev | 类型化选择题，候选是会话卡，选项含 `new` / `none` | gpt-6-luna |
| Super Agent | accept / attach / ignore / stop | DeepSeek |
| Jev + Super Agent | 仍是 Super Agent 的路由，只把模型换成 Jev 用的决策模型 | gpt-6-luna |
| 补充 | Jev 的选择题 | DeepSeek |

「Jev + Super Agent」不是把两种协议接成一条流水线。它是用 gpt-6-luna 去跑 Super Agent 的路由，用来和「DeepSeek 跑 Super Agent」「gpt-6-luna 跑 Jev 选择题」对照，把协议和模型拆开。

模型格子各跑 3 次，表里是均值，括号是最小到最大。词法基线是确定的，只跑 1 次。Jev 协议的会话卡是标题（首条消息前 80 字）、最近一问和最近一答。Super Agent 沿用它原来的卡片。每次 23 次调用，Super Agent 偶有重试到 25 次，单次整轮 90–105 秒。数据集里没有停止类消息，所以没测 `stop`。

### 指标在问什么

分数由脚本从预测算出，没有人工判分。

- **会话纯度**：消息进了某个会话，且该会话里没有别的原始会话的消息，才算对。被忽略或拒绝算错。
- **attach 精确率**：只看附着。目标会话在附着之前是否只含同一原始会话。新建和忽略不计入。
- **续接命中率**：前面已经出现过同一原始会话的 17 条里，有多少被附着到纯净的同源会话。把「同一会话里的新请求」另开，也记为没命中，所以这个指标偏严。
- **B³ P / R / F1**：每条消息单独算再平均。被忽略或拒绝的消息各算一个单独的簇。全并成一个会话时召回高、精确率低；每条各开一个会话时精确率高、召回低。
- **跨项目合并**：一个会话里同时出现两个项目的消息，计 1 个。

精确率一类（纯度、attach 精确率、B³ P）问「并进去的对不对」。召回一类（续接命中率、B³ R）问「该并的并了没有」。B³ F1 把两边折中，四个模型格子几乎一样，区分不了方法。看纯度和跨项目合并更合适。

| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| baseline（词法） | 0.043 | 0.000 | 0.000 | 0.206 | 0.935 | 0.337 | 1.0 | 0 | 2 |
| Jev | 0.246（0.17–0.39） | 0.333（0.29–0.41） | 0.333（0.29–0.41） | 0.584 | 0.667 | 0.622（0.60–0.67） | 2.7（2–3） | 1.7（1–2） | 4.3 |
| Super Agent | 0.986（0.96–1.00） | 1.000 | 0.392（0.35–0.47） | 1.000 | 0.457 | 0.626（0.59–0.67） | 0 | 0.3（0–1） | 16.0 |

### 从这张表能带走的结论

1. 三种方法都明显高于词法。词法几乎把消息并进一个会话，纯度 0.043，最后只有 2 个会话。
2. 纯度来自 Super Agent 的协议，不是来自换一个更强的模型。DeepSeek 跑这套路由时，attach 精确率 1.000，跨项目合并是 0。换成 gpt-6-luna 之后，纯度降到 0.899，每轮大约还有 1 个混项目会话（第 1 轮是一条 Hy-Memory 被并进 MemOS）。Jev 的选择题无论用 gpt-6-luna 还是 DeepSeek，纯度都只有 0.25–0.39，每轮 2–3 个混项目会话。
3. Jev 选择题倾向于并入，也会丢掉请求。选项只有已有会话、`new`、`none`，没有「必须指向这个会话才能附着」的约束，所以只形成 4–6 个会话，把不同项目吸到一起。`none` 会丢掉完整请求：Jev 每轮都丢掉 t04（Codex 连接失败）。
4. Super Agent 偏保守。6 个原始会话被拆成 16 个，续接命中率 0.392，B³ 召回 0.457。它把主题相似的新请求另开，这符合它的设计，也说明对人来说会显得过碎。
5. B³ F1 在四个模型格子里是 0.62–0.67，分不出高下。金标按原始会话划，一个会话里本来就有互不相关的请求：并得多的方法召回占便宜，拆得碎的方法精确率占便宜。
6. 用 Jev 的模型去跑 Super Agent 的协议，没有超过原来的 Super Agent。纯度 0.90 对 0.99，差距大于单格 3 次的波动。续接命中率 0.45 对 0.39，落在波动里，不能说更好。

样本只有 23 条、6 个会话、每格 3 次。续接命中率和 B³ F1 的小差距在噪声里。Super Agent 以前人工判过 0.913，用的是更宽的「同一件事」规则，不能和本表的会话纯度直接比。Jev 在主题卡上的 0.882 也是另一个任务。

## 10. topic 切分的粗细是一个跷跷板

上面这张表就是这个跷跷板的一次测量。

切得细，topic 里的纯度高，add 和查询时不容易选错。Super Agent 就是这一端：纯度 0.986，没有跨项目合并，但 6 个原始会话变成 16 个。人要审计、要在界面上扫一遍，会看到一长串很碎的 topic。

切得粗，人看得少，方便审计和可视化。Jev 的选择题和词法基线是这一端：会话只有 2–6 个，但纯度掉到 0.04–0.39，不同项目的消息被吸进同一个会话。topic 一杂，后面的归属和检索就会选错，因为候选卡本身已经混了。

B³ F1 在两端差不多，所以不能用一个 F1 决定切多细。精确率高的一端召回低，召回高的一端会并错。

推荐的做法是双层映射，而不是在「很细」和「很粗」里只留一层：

- Agent 做 add 和查询时，用切得细的 topic。归属和检索对着这层，保证纯度，减少选错。
- 另用一个整理模型，把细 topic 归纳成给人看的 topic 列表。审计、可视化和产品界面读这层。
- 给人看的列表是细 topic 的视图，不反过来当 Agent 匹配用的键。否则又回到「为了好看把不该并的并在一起」。

这是这次实验之后的建议，还没有写进 v3，也没有在当前代码里做。真要做，需要单独定两层的 id 怎么对应、整理模型什么时候跑、人改了粗 topic 之后细 topic 跟不跟随。

## 12. 和同事对齐时建议先看的四件事

1. 讨论效果时先分清：这是 `--oracle`、阅读上限，还是产品回放。现在能说满的是阅读上限的 `answers.llm`，不能说产品的 `entries.f1` 或 Recall@3 已经变好。
2. q03 的 1.000 含评委宽容；q24 的标准答案和 R-02、R-03 不是同一句。
3. 搜项目必须带 project 视图。省略视图不会落到项目记忆。
4. Jev 选题的 0.882、会话消融里的纯度，和产品 `entries.f1` 不是同一个数。切 topic 的粗细是跷跷板：Agent 用细 topic，给人看的列表再由整理模型归纳。这还不是已定规格。

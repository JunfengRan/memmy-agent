## 1. 现在能对同事说的话

1. 讨论效果时先说清测的是哪一种：评分器自检、阅读上限，还是产品先写入再检索再作答。三者的满分含义不同。
2. 现行口径下，当前版本两次端到端的 `entries.f1` 是 0.816 和 0.861，Recall@3 是 0.871 和 0.903，`answers.llm` 是 0.645 和 0.742。阅读上限（金标按提问时刻渲染后交给 DeepSeek）的 `answers.llm` 是 1.000，rubric 是 0.935。上限不是产品成绩。数字在 [metrics.md](metrics.md)。
3. 搜项目必须在请求里带上 project 视图。省略 `include_memory_view` 时走用户记忆和 L1/Skill。
4. 当前运行有过度拆分，旧实现又有误并和漏写；粒度要同时看纯度、召回与决策状态。可以讨论保留算法主题、另做给人看的归纳，不能从主题数直接断言越细越好。这还没写进 v3，代码里也没有。

## 2. 一个分数在测什么

同一个 `answers.llm`，三种跑法：

| 跑法 | 记忆从哪来 | 分数说明什么 |
| --- | --- | --- |
| `--oracle` | 把标准答案写进 run | 评分器认得自己的金标。这项一定是 1 |
| 阅读上限 | 每个提问时刻的金标 `topic_detail_list` 交给阅读模型，再交给评委 | 阅读模型或评委自己会丢的分。实现没有参与 |
| 产品回放 | 产品 add 写下的记忆，再 search，再作答 | 写入、检索、回答叠在一起的结果 |

`entries.f1` 只属于最后一种里的写入。评委先判断系统写下的决策、经验、进展是不是金标里的同一件事，再一对一配对。召回率看该写的有没有写上，精确率看写下的有多少是该写的，F1 是两者的调和平均。门槛默认 0.8。

`answers.llm` 是评委看事实有没有说对。`answers.rubric` 是 `mustInclude` 必须逐字出现。同义改写可以 llm 对、rubric 错。看上限看 `answers.llm`。拿 rubric 当门槛时，换一种说法就算错。

上一口径在 v2.1 上把上限做到 `answers.llm` 1.000 时，rubric 是 0.871（27/31）。四道没逐字命中、评委仍判对的题：

- q03：多了一个逗号，「没有客户名时，这笔不进月报」。
- q04：「会留下」说成了「保留」。
- q05：「整数分」被引号隔开。
- q41：「队尾」说成了「末尾」。

v2 的 0.826 和 v2.1 的这三行逐题对不上：数据集、题数、阅读模型都换了。

阅读提示词 v2 加了一句通用规则：问题问某项测试或规则现在怎么写，而决策里已经有这条规则时，用决策回答，不要因为没贴出代码就说没有相关内容。提示词里没有金标原句。

**评委可以否掉已经说对的答案。** q24 问 catalog 的价格表为什么要加一列金额。阅读模型已经说出：价格查询太慢，给 price 表加 amount 列，列表直接读这一列。评委的理由是「这是另一张表、另一个需求」。记忆里的决策写的就是 price 表。当时的标准答案没写出这几个字，评委自己补了一个「catalog 表」，再判定两者不同。标准答案改成和 `dec_price` 同一组事实、只把原因放到句首之后，同一评委判对。R-20261110-02 和 R-20261110-03 用的是改之前的答案。这是 v2.1 内的小改，没有另冻一份数据集。

同一道题、同一份回答，抽查时判对、全量跑时判错，也出现过一次。温度 0 不能当成「再跑一次结果一定一样」。

**「测试怎么写」和「规则是什么」会被读成两件事。** q03 和 q04 是同一句问话，问的时刻不同。q03 在 12:00，记忆里只有「没有客户名时这笔不进月报」，以及测试已补充，没有测试代码。q04 在更晚的时刻，两条规则还没裁决。提示词 v1 时，阅读模型对 q03 回答「记忆中没有相关内容」。提示词 v2 之后，它说出了规则，后面仍加了一句「无法说明断言和用例是怎么写的」。评委把整段判对。所以上面的 1.000 包含这一处宽容。换评委或换阅读模型时，q03 要再看一眼。

## 5. 代码里已经这样跑

细节在 ADR 和 [open-questions.md](open-questions.md)。

**整理。** 每个任务只抽取一次。主题集合变了，重跑召回和归属，不重抽。版本冲突只重跑判断，最多 3 次，不重放旧的 ChangeSet。候选并集上限 20，标成必须考虑的主题不会被这层上限丢掉。同一 Space、同一 domain 集合里已经整理过的消息只作上下文。进度里没有 `domains` 的旧任务不参与这次去重，缺字段不是空集合。

**检索。** 三路按名次做 RRF，k=60，不拼各路原始分数，也不用模型重排。relativity 是这次融合分除以这次最高分，再按输出顺序取到目前为止的最小值，所以列表上的 relativity 不会回升。公开结果没有 `score`。省略 `include_memory_view` 时不搜项目；要搜项目必须显式带上 project。这个缺省不在 Q-28 原来的提议里，代码已经这样做，仍等设计确认。三路共用 1200 ms 超时，project 也在内。超时后主题列表为空，并在 `degraded` 里记下 project。底层检索可能在返回之后仍写入 `recall_log`。一条过期向量会让整次项目召回退回词法，这是 v3 §3.5.1 的现行为，Q-30 还没改。

**注入。** 字段里如果出现字面的 `</project_index>` 或 `<memos_context`，会把块提前闭合，剥离时删错一段。这两类标签都换成全角。未闭合的标签原样留下并计数。

**任务与决策。** 没有 `chat_time` 时用到达时间的秒，同一秒、同一段文本仍是一条任务。可重试失败（模型调用失败、版本冲突耗尽）再提交会新建任务，只重跑失败的 Space。新任务上的条数只含这次重跑的 Space。非作者、未被认可的不同结论进 conflicts，不改写更晚的决策。内容作者加入已有分歧、从而把当前内容的成员挪空，这条路径还没改，记在 Q-23，对应用例是 `it.todo`。

## 6. topic 切分的粗细是一个跷跷板

细分通常有利于保持单题纯度，但也可能拆散同一决策，使后续改写和裁决找不到旧结论；人审计时也会看到很碎的列表。粗分减少列表长度，却可能混入不同工作，影响归属和检索。当前案例同时有这两类风险，不能只凭主题数确定粒度。B³ F1 把精确率和召回折中，两端可以差不多，所以不能用一个 F1 决定切多细。

运行 B 实际写下的 58 个主题、决策和冲突在 [algorithm-handoff.html#gallery](algorithm-handoff.html#gallery)。图上的主题数和 B³ 来自两次当前版本加旧实现的评分。卡片没有逐主题标拆开或误并：和金标逐字相等只能对上 2 条必写条目，对不上报告里的 9 和 3。

建议做双层映射，两层都留下：

- Agent 做 add 和查询时，用切得细的 topic。归属和检索对着这层。
- 另用一个整理模型，把细 topic 归纳成给人看的列表。审计、可视化和产品界面读这层。
- 给人看的列表是细 topic 的视图，不反过来当 Agent 匹配用的键。

这是实验之后的建议，还没有写进 v3，也没有在当前代码里做。真要做，需要单独定两层的 id 怎么对应、整理模型什么时候跑、人改了粗 topic 之后细 topic 跟不跟随。

下面这张表是同一种取舍的一次测量，测的是会话路由，不是产品 add。材料在 `eval/session-router-ablation/README.md`（2026-11-09，分支 `feat/superagent-session-router`）。该实现已合入 `codex/jev-superagent-consolidated`；脚本在整合分支可直接跑，历史证据位于 `eval/session-router-ablation/results/`。新的输出写忽略目录，不覆盖历史结果。

数据集是 23 条消息、6 个 Cursor 会话，按轮转交错。金标是「这条消息来自哪个原始会话」。同一个原始会话里可以有互不相关的请求，所以金标不是「同一件事」。模型格子各跑 3 次，表里是均值，括号是最小到最大。词法基线是确定的，只跑 1 次。数据集里没有停止类消息，所以没测 `stop`。

两种协议：

- **Jev** 把归属做成选择题。候选是已有卡片，选项还有 `new` 和 `none`。产品开关 `MEMMY_DECISION_TOPIC` 默认关闭。gpt-6-luna 不接受温度 0，请求里不传温度。
- **Super Agent** 的动作是 accept、attach、ignore、stop。不确定就新建。提示词版本 `2026-11-06.1`。原来的实验用 DeepSeek，温度 0。

表里的「Jev + Super Agent」是用 gpt-6-luna 去跑 Super Agent 的路由，用来把协议和模型拆开。它不是两条流水线接在一起。

分数由脚本从预测算出，没有人工判分。会话纯度问「并进去的会话里有没有混进别的原始会话」。续接命中率问「该接回的有没有接回」，把同一会话里的新请求另开也算没命中。B³ F1 在四个模型格子里几乎一样，区分不了方法。看纯度和跨项目合并更合适。

从这张表读出四件事：

1. 词法几乎把消息并进一个会话，纯度 0.043，最后只有 2 个会话。三种模型方法都高于它。
2. 在这批样本中，Super Agent 协议在两个模型下都获得更高纯度，提示协议是重要因素；两种协议卡片也有差异，不能据此排除模型与上下文的影响。DeepSeek 跑这套路由时 attach 精确率 1.000，跨项目合并是 0，6 个原始会话被拆成 16 个。换成 gpt-6-luna 之后纯度降到 0.899，差距大于单格 3 次的波动。续接命中率 0.45 对 0.39，落在波动里。
3. Jev 的选择题倾向于并入，也会丢掉请求。gpt-6-luna 和 DeepSeek 的纯度都只有 0.25–0.39，会话只有 4–6 个，每轮 2–3 个混项目会话。`none` 会丢掉完整请求：Jev 每轮都丢掉 t04（Codex 连接失败）。
4. B³ F1 在四个模型格子里是 0.62–0.67。金标按原始会话划，一个会话里本来就有互不相关的请求：并得多的方法召回占便宜，拆得碎的方法精确率占便宜。

样本只有 23 条、6 个会话、每格 3 次。Super Agent 以前人工判过 0.913，用的是更宽的「同一件事」规则，和本表的会话纯度不是同一个数。

Jev 还有一次自己的选题评测（专项实验 R-20261106-01），候选是数据集 v2 的金标主题卡，不经过产品 add/search。add 归属 0.882（30/34）：已有主题 21/21，新建 3/5，无关 6/8。同一批卡片上，search 选中 Recall@1 是 0.826（19/23），词法对照是 0.522。这个 0.882 是主题选择题的准确率，不是产品的 `entries.f1`，也不能和上面的会话纯度横比。
